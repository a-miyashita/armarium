# 02. Architecture

- Status: Draft

## 1. Overall structure

```
┌──────────────────────────── armarium.exe (Tauri 2) ────────────────────────────┐
│  WebView2 (React + TS)                         Rust (src-tauri)                  │
│  ┌───────────────┐   Tauri IPC (invoke /    ┌──────────────────────────────┐   │
│  │ SourceTree    │   events, JSON)          │ commands.rs (thin adapter)    │   │
│  │ DataGrid      │ ───────────────────────▶ │                              │   │
│  │ SqlEditor     │ ◀─────────────────────── │   armarium-core (library)     │   │
│  │ ResultGrid    │                          │   ├ workspace  ├ ingest       │   │
│  └───────────────┘                          │   ├ engine     ├ edit         │   │
│                                             │   ├ sql        └ persist      │   │
│                                             │            │                 │   │
│                                             │   SQLite (session database)   │   │
│                                             └──────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────────────────┘

┌──────── armarium-mcp.exe (stdio) ────────┐
│ rmcp server ─▶ armarium-core ─▶ SQLite   │   ← An MCP client (for example, Claude Desktop) starts it
└──────────────────────────────────────────┘
```

- All domain logic is in `armarium-core`. The GUI and the MCP server share it ([ADR-0004](../adrs/0004-cargo-workspace-layout.md)).
- The GUI and the MCP server are different processes. Each process has its own session database (SQLite) ([ADR-0013](../adrs/0013-mcp-server-mode.md)).
- The two processes share only the data files and the workspace settings (`workspace.json`).

## 3. Modules of armarium-core

| Module | Responsibility |
|---|---|
| `workspace` | Register and unregister sources. Keep the tree structure. Assign SQL names. Read and write `workspace.json`. |
| `ingest` | Read files into SQLite. Detect and convert the encoding. Detect the CSV dialect. Read Excel files. Infer column types. |
| `engine` | Manage the SQLite connections (one connection for writes, one or more for reads). Configure the connections. Create and drop tables. Fetch pages of rows. |
| `edit` | Apply edit operations. Undo and redo (with changesets from the session extension). Track the dirty state. |
| `sql` | Run user SQL (the authorizer checks it). Load tables that are not loaded yet. Keep query results. |
| `persist` | Write data from SQLite to files. Reproduce the dialect. Replace files atomically. Detect changes by other programs. |
| `model` | Shared types (`SourceId`, `TableId`, `ColumnSchema`, `LogicalType`, `CellValue`, `Dialect`, and others) |

In the code, the modules are: `workspace`, `ingest` (with `csv`, `encoding`, and `excel`), `db` (connections,
authorizer, changesets), `engine` (the public `Engine` API, with `edit`, `persist`, and `views`), `sql`,
`model`, `naming`, `format`, and `fsutil`.

### 3.1 Main types (outline)

```rust
// Pseudo-code. We decide the final form during implementation.
struct Source {
    id: SourceId,            // UUID v7
    path: PathBuf,           // Absolute path
    kind: SourceKind,        // Csv | Excel
    options: SourceOptions,  // Dialect overrides, header row, type overrides, and others
    tables: Vec<TableRef>,   // CSV: 1 table. Excel: 1 table for each sheet
}

struct TableRef {
    id: TableId,
    sheet: Option<String>,   // Excel sheet name
    sql_name: String,        // Example: "sales" or "budget_2026"
    state: LoadState,        // Unloaded | Loaded { dirty: bool } | Error(..)
}

struct ColumnSchema {
    display_name: String,      // Header text in the file (written when the file is saved)
    sql_name: String,          // SQL identifier (no duplicates, not empty)
    logical_type: LogicalType, // Integer | Real | Text | Date | DateTime | Boolean
    type_source: TypeSource,   // Inferred | UserOverride
}
```

## 4. Session database

For details, see [ADR-0003](../adrs/0003-sqlite-as-engine.md) and [ADR-0006](../adrs/0006-working-copy-edit-model.md).

- Location: `%LOCALAPPDATA%\Armarium\tmp\session-{pid}-{random}.db`. Each process holds a lock on `session-{pid}-{random}.lock`. Armarium deletes the files when it stops. At start, Armarium deletes the files of other sessions whose lock is free (old files that remain after a crash).
- Settings: `journal_mode = WAL`, `synchronous = OFF`. Armarium sets `cache_size` from the size of the physical memory.
- Objects in the database:

| Name | Type | Purpose |
|---|---|---|
| `"{sql_name}"` | STRICT table | The working table. It has only the columns of the file. The row ID is `rowid`. |
| `__arm_ord_{table_id}` | Table | The order of the rows (`rid`, `ord`) |
| `__arm_ord_{table_id}_ins` and `_del` | Triggers | Keep the order table up to date |
| `__arm_base_{table_id}` | Table | The `rowid` of each line of the file as it was read or last saved (`line`, `rid`). `diff_table` uses it. |
| `__arm_view_{n}` | Table | The result of a sort or filter in the grid (`pos`, `rid`) ([ADR-0014](../adrs/0014-paged-grid-ipc.md)) |
| `__arm_res_{n}` | Table | The result of a SELECT statement ([07. SQL](07-sql.md)) |
| `__arm_stage` | Table | A temporary table for reading a file (all columns are TEXT) |

## 5. Data flow

### 5.1 Open a table

1. The user selects a table in the left pane.
2. The UI calls `open_table(table_id)`. If the table is not loaded, the core runs `ingest`:
   - It reads the file, converts the encoding to UTF-8, and inserts the rows into a temporary table ([ADR-0008](../adrs/0008-ingestion-in-rust.md)).
   - It infers the column types and creates the working table ([ADR-0007](../adrs/0007-round-trip-safe-typing.md)).
3. The core returns the schema and the total number of rows.
4. The grid fetches only the visible rows with `fetch_rows(table_id, view_id, offset, limit)` ([ADR-0014](../adrs/0014-paged-grid-ipc.md)).

### 5.2 Edit

1. The user edits a cell in the grid. The UI calls `apply_edit(table_id, EditOp)`.
2. The core converts the operation to SQL and runs it in a transaction. The session extension records a changeset, and the core pushes the changeset on the undo stack.
3. The core sends a `table-changed` event to the frontend. The frontend updates the dirty mark and the number of rows.

### 5.3 Save

1. The UI calls `save_table(table_id)`. `persist` checks whether another program changed the file.
2. `persist` reads the working table in row order and writes it to a temporary file in the dialect of the source. Then it replaces the original file atomically.
3. `persist` updates the fingerprint of the file and clears the dirty state.

### 5.4 SQL

1. The UI calls `run_sql(text)`. `sql` prepares the statements one at a time. If the authorizer does not allow an operation, the prepare step fails ([ADR-0009](../adrs/0009-sql-sandbox.md)).
2. If a statement refers to a table that is not loaded, `sql` loads the table and prepares the statement again.
3. For SELECT, `sql` keeps the result in a result table and returns it in pages. A DML statement changes the working table, and `sql` pushes the change on the undo stack.

## 6. Concurrency and threads

- A mutex in the core protects the write connection and the state of the tables. Write operations run one at a time. (This has the same effect as a dedicated worker thread with a channel, and is simpler.)
  - Reason: this keeps the edit operations, the undo stack, and the authorizer switching consistent in a simple way.
  - The Tauri commands and the MCP tools call the engine on blocking threads, so the IPC thread does not wait.
- A separate read connection handles page fetches (`fetch_rows`). Because the database uses WAL, the user can scroll while a heavy query or a file read runs.
- Long operations (reading a large file, running a heavy query) send progress events. The user can cancel them (`sqlite3_interrupt`).

## 7. Error handling

- The core defines typed errors (`CoreError`) with `thiserror`. At the IPC boundary, the core converts each error to JSON with a code and a message.
- Example error codes: `FILE_NOT_FOUND`, `FILE_LOCKED`, `ENCODING_UNDETECTED`, `EXTERNAL_MODIFICATION`, `SQL_FORBIDDEN`, `SQL_ERROR`, `TYPE_MISMATCH`.
- The UI selects the display from the code. The UI translates the message with an i18n key.

## 8. Logs

- Armarium uses `tracing` and writes rotated logs to `%LOCALAPPDATA%\Armarium\logs`.
- Logs do not contain cell values or query results. SQL text is logged only at the debug level.
